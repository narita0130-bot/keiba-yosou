## 4. 毎日の運用手順

作業ディレクトリ：`/home/user/keiba-yosou`、ブランチ：`claude/restore-lost-data`
**numpyはコンテナ付属のものが壊れているので `PYTHONPATH=/opt/np` を付ける。**

### 4-1. 朝：投稿を受け取ったら

```bash
# ① 開催の確認（race_idの接頭辞）
python3 -c "import sys;sys.path.insert(0,'scripts');from fetch_odds import kaisai_prefixes;print(kaisai_prefixes('2026-09-27'))"

# ② 非馬：印を data/<日付>.ev.json に書く（馬番は出馬表で照合してから）
#    形式：{"date":..., "races":[{"race_id":..., "stars":"★★", "marks":{"4":"◎","5":"◯","11":"▲"}}]}

# ③ Logic：note本文を data/<日付>.logic.txt に置いて馬番を解決
python3 scripts/parse_logic.py --text data/<日付>.logic.txt --out data/<日付>.logic.json
#    （取りこぼしたら同じコマンドを流し直せば差分だけ埋まる）

# ④ 買い目を組む
python3 scripts/build_orders.py --ev data/<日付>.ev.json --out data/<日付>.orders.json

# ⑤ CSVを出す（投票入力用と記録用）
PYTHONPATH=/opt/np python3 scripts/build_bets_csv.py --orders data/<日付>.orders.json \
    --ev data/<日付>.ev.json --out data/<日付>.autofill.csv --format autofill
PYTHONPATH=/opt/np python3 scripts/build_bets_csv.py --orders data/<日付>.orders.json \
    --ev data/<日付>.ev.json --out data/<日付>.bets.csv
```

### 4-2. 締切前
朝のオッズは薄商いで歪む（馬連と馬単で25%の組が1.5倍以上ずれることがある）。
**締切の30〜60分前に④⑤を流し直す。** 買い目は変えない。

### 4-3. 投票
`autofill.csv` を **Chrome拡張「JRA CSV 自動入力」** で即PATに入力する。
**「投票」ボタンは必ず人が押す**（§13）。

### 4-4. レース後

```bash
# ⑥ 結果を確認
python3 scripts/fetch_result.py --race <race_id>

# ⑦ 収支を精算
python3 scripts/settle.py --bets data/<日付>.bets.csv --out data/<日付>.settle.csv

# ⑧ 印の成績を記録（非馬・Logic・その他の情報源）
python3 scripts/record_marks.py --ev data/<日付>.ev.json --logic data/<日付>.logic.json \
    --picks 複勝専門店=data/<日付>.fukusho.json

# ⑨ 累計を確認
PYTHONPATH=/opt/np python3 scripts/marks_stats.py

# ⑩ コミットしてプッシュ（コンテナは予告なく回収されるので必ず）
git add -A && git commit -m "..." && git push -u origin claude/restore-lost-data
```

## 7. 買い目の作り方

### 7-1. テンプレート（非馬の印から機械的に）

| 式別 | 組み方 | 相手 |
|---|---|---|
| 馬連 | ◎軸流し | ◯▲△（☆は入れない） |
| 馬単 | ◎1着固定流し | ◯▲△☆ |
| 3連複 | ◎1頭軸流し | ◯▲△☆ 全員の C(n,2) |

☆の扱いは非馬本人の記述「☆は基本的に3連系用（本命馬からの馬単の相手には流す可能性あり）」に従う。

### 7-2. 決まっていること

- **買う式別は 馬連・馬単・3連複 の3つだけ**（ワイド・3連単・単勝・複勝は買わない。9/13決定）
- **金額は全点100円**（JRAの最低単位は100円）
- **序列の明記がない3頭はボックスで組む**（9/20 阪神10Rで、◎軸流しにしたため馬連5-12の500円を買い逃した）
- **1頭しか挙がっていないレースは組めない**（相手がいない）

### 7-3. 分かっている弱点

- 全部が◎軸なので、**1着に無印が来ると全点即死**する（9/20は5レース中4レース、9/22は5レース全部）
- 非馬の印が1-2着を独占しても、◎が入らなければ取れない（12%のレースで発生）。
  ただし「相手同士」を足すと93レースで75.0%に下がるので、**足さない**
- **「全点100円」は中立ではない。** 人気薄の比重がプールより高く、それだけで約7ポイント損をしている（§11-4）

## 8. EVエンジンとその限界

- 基礎能力を**単勝オッズのlog正規化（50〜80）**＋**印の加点**（◎+8 ◯+5 ▲+3 △+2 ☆+2）で作る
- 鋭さγは**市場とのKL距離が最小になるよう**自動調整
- EVは Plackett-Luce（Henery補正）で計算し、市場75%＋モデル25%を混ぜる
- 判定：🟢買い＝頑健下限≥1.0 ／ 🟡見かけ＝中心EV≥1.0 ／ ❌見送り

### ⚠️ 限界

**構造上、市場のコピーである。** 独立した情報は印の加点だけで、その印（非馬）に情報がないことは
測り終わっている。実績でも **EVの値と払戻の相関は r=+0.027**（254点）。

**🟢買いの表示に根拠はない。** 表示をやめるか「未検証」と書くことを推奨（§15）。

## 9. 記録と検証の仕組み

### 9-1. 印の成績を「同じ人気構成の無作為」と比べる

控除率20%は**プール全体**の話。1頭ずつ均等に買うと人気で回収率が大きく違う：

| 人気帯 | 単勝 | 複勝 |
|---|---|---|
| 1人気 | 79.3% | 90.0% |
| 2-3人気 | 79.1% | 80.5% |
| 4-6人気 | 74.3% | 70.6% |
| 7-9人気 | 77.4% | 70.9% |
| 10人気以下 | 63.8% | 59.3% |
| **全体** | **72.2%** | **69.3%** |

`marks_stats.py` はこの `baselines.json` を使い、**その予想家と同じ人気構成で無作為に買った場合**と比べる。
**一律80%と比べるのは誤り**（人気薄の多い予想家を不当に低く見る）。

### 9-2. 測るときは複勝

組み合わせ馬券は1点あたりSDが956で、5%の優位を確かめるのに**5.5年**かかる。
複勝ならSDが140〜174で、必要な点数は**数十分の1**。

### 9-3. 事前登録

新しい情報源や買い方を試すときは、**データを見る前に**判定基準をコミットする。

| 文書 | 対象 | 結果 |
|---|---|---|
| `docs/prereg_logic.md` | Logicの注目馬 × 複勝。範囲・欠けの扱い・合格条件を先に固定 | **不合格**（26日1,355点・93.2%） |
| `docs/prereg_model.md` | オッズを使わないモデル。期間分割・禁止情報・2段階判定 | **検証期間を開けずに終了** |

**採用条件（複勝）：300点以上 かつ 回収率の −1SE が100%超。**

## 10. オッズを使わないモデル（2026-09-20〜21、終了）

「予想家の印では勝てない、ならば自分で確率を作る」という取り組み。

| 段階 | 内容 | 担当 |
|---|---|---|
| データ | 2024-01〜2026-09、9,447レース／130,120行を収集 | Claude |
| M1 設計 | 192特徴量（前走・条件別実績・騎手厩舎・馬体重など）。**単勝オッズ・人気は禁止** | 別AI → 監査 |
| M2 生成 | 学習期間のみ・日付境界 `<`・同日/未来/オッズの不変性テスト | 別AI → 監査（再実行で確認） |
| M3 選択 | 候補3件を事前固定 → 時系列交差検証 → `logistic_c01` | 別AI → 監査（再実行で確認） |
| 判定 | 学習期間内で市場と比べて決定的に負け → **検証期間を開けずに終了** | ユーザー判断 |

**結果：** モデル単独は市場に0.25 nats負け。市場と組み合わせても、モデルの重みは **α≈0**（市場を知っていれば何も足さない）。
**レース前の公開データを機械的に並べても、市場の知らない情報は出てこない。**

役割分担（実装は別AI、監査はClaude）は `docs/REVIEW_protocol.md`。

## 12. 誤りと教訓

この1ヶ月でClaudeが犯した主な誤り（詳細は `docs/REVIEW_fundamental.md` §6）：

1. 最初期、GPTの読みに合わせて独立に判断していなかった
2. **比較基準を一律80%とした**（実際は人気で59〜90%）→ 予想家の評価を誤った
3. **「非馬の◎は最弱の印」と繰り返した**（人気構成の違いを実力と取り違え）
4. **Logicの選別力を過小評価**
5. モデルの判定を「単独で市場に勝つか」にした（正しくは「組み合わせて上回るか」）
6. **「検証期間は未開封」と書いたが、前日に1,933頭分を集計済みだった**
7. データ収集のパーサーが分析表を着順行と誤認し12%が破損（健全性チェックで発見）
8. 読み込みタイムアウトで一括処理が落ちるバグ（2回停止。9/24修正）

### 教訓

- **事前登録は「後から基準を動かさない」には効くが、「最初の基準が正しいか」は守らない**
- **3通り試して1つが100%を越えたら、それは罠の形**（Logic複勝108%→93%、一致/食い違いの符号反転、3連複◎◯▲の348%、傾斜の104%）
- **1回の悔しさを一般化しない**（9/20の500円は実在の取りこぼしだが、埋めると損）
- **良すぎる結果は、合格ではなくバグの兆候として扱う**
- **健全性チェックを飛ばさない**

## 13. 絶対に守るルール

### 安全
- **「投票」ボタンは絶対に自動で押さない。** Chrome拡張は入力までで止め、押すのは人
- **認証情報（加入者番号・暗証番号・P-ARS番号）を外部に保存しない。** クラウド側に置く設計は取らない
- **重複入力防止ガードを外さない**

### データ
- **オッズ・馬番・着順・払戻を推測で埋めない。** 取れなければ「取得不可」と書く
- **馬番は必ずnetkeibaの出馬表で照合する**
- データを追加したら、**レースごとに 行数 == `field_size`** を確認する
- **エンジン本体（`keiba_engine_v2.py`）は改変しない**。使う前に回帰テスト21項目

### 検証
- **検証期間は、判定の瞬間まで開かない**
- **2026-04〜09 は次の検証期間に使わない**（すでに予想家の分析で結果を見ている）
- 複数の案を試して一番良いものを選ばない。落ちても基準を変えて再挑戦しない
- 比較対象は理論値ではなく、**実測した同条件の無作為**にする
- 予測の価値は**「市場と組み合わせて上回るか」**で測る

## 15. 推奨と今後

### 推奨（`docs/REVIEW_fundamental.md` §8）

**月の予算を決めて娯楽として続ける。ただし中身を変える。**

1. **月の上限を先に決める**
2. **🟢買いの表示をやめるか「未検証」と書く**
3. **本線を非馬からLogicに移すか、少なくとも同等に扱う**
4. 大きな当たりを狙う日は組み合わせ、損を抑えたい日は複勝、と目的で使い分ける
5. 損を減らしたいなら**人気薄の組み合わせを削る**（§11-4）
6. **その日の当たり外れで買い方を変えない**

「勝つ」をまだ目指すなら、**買わずに記録だけ続ける。** 本物の優位が現れれば記録に必ず出る。
